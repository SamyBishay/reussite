# The connector

A remote MCP server inside the relay Worker (`relay/src/connector/`). An AI app the person already pays for (Claude first) reads and edits their list through it, at no AI cost to Réussite. Brief §10. It stays off until the person switches it on.

## How it fits together

```
AI app ──OAuth 2.1 + DCR──▶ /oauth/register, /authorize (pairing code), /oauth/token
       ──Bearer token──────▶ /mcp  (Streamable HTTP, stateless, JSON responses)
                                │ props {spaceId}
                                ▼
                  decrypt the snapshot's hot part + later batches ──▶ tools ──▶ one encrypted batch, device "connector"
```

- `@cloudflare/workers-oauth-provider` (pinned) sits in front of the Worker. It owns `/oauth/*`, the discovery documents (`/.well-known/oauth-authorization-server`, `/.well-known/oauth-protected-resource/mcp`) and token checks; storage is the KV namespace `OAUTH_KV`. Everything else goes to `handle` in `relay/src/index.ts`.
- `/mcp` is built with `createMcpHandler` from `agents/mcp/server` (stateless, no Durable Objects) over `@modelcontextprotocol/server` 2.x, which is what that version of the Agents SDK takes. A server with its ten tools is built for every request; that costs about 1 ms.
- Tool input is validated by zod schemas; change-sets by the app's own `ChangeSchema` (`src/ai/changeset.ts`) and planned by the app's own `planChanges` (`src/ai/apply.ts`). What a write means (`finishEffects`, `newTaskFields`, `nextOccurrence`, `projectCompletes`, `dueRulePatches`) is in `src/domain/effects.ts`, shared with `src/app/actions.ts`; the read rules are in `src/domain/lists.ts`, shared with `src/app/model.ts`. The Worker has no copy of the data model, merge, change-set schema or validation.

## Switching on and off (app → relay)

`Authorization: Bearer <auth secret>` as for sync. Types are in `src/sync/protocol.ts`.

| | |
| --- | --- |
| `POST /v1/spaces/:space/connector` `{key}` | `key` is the space's raw 32-byte encryption key, base64url (`SpaceKeys.encKeyRaw`). The relay checks that it opens what the space already holds (409 `wrong_key` if not), stores it and the auth secret wrapped with AES-GCM under `CONNECTOR_WRAP_KEY` (D1 table `connector`), registers the device `connector` with the encrypted label `{name: "Connector"}`, and returns 201 `{on: true, code, expires, url}`. `code` is `ABCD-EFGH`, shown once; `url` is what to add in the AI app. 503 `connector_unavailable` if the secret isn't set (nothing is stored). Safe to repeat. |
| `POST …/connector/code` | A fresh code `{code, expires}`. 409 `connector_off` if the connector isn't on. |
| `GET …/connector` | `{on, lastUsed, url}`; `lastUsed` is ms or `null`. |
| `DELETE …/connector` | Deletes the wrapped key, codes, pending confirmations, undo records and the `connector` device row, then revokes every grant and token of the space at once (`listUserGrants` / `revokeGrant`, with the space id as the user id). `{ok: true, revoked: n}`. |

"Delete everywhere" (`DELETE /v1/spaces/:space`) does the same, and the connector's tables are in `SPACE_TABLES`. The rate limits of sync apply (60 writes a minute per space, per IP).

The pairing code is 8 characters from `ACDEFGHJKMNPRTVWXY34679` (no 0 O Q, 1 I L, 2 Z, 5 S, 8 B, U), single use, valid 10 minutes, kept only as an HMAC under the wrap key. At most three unused codes per space.

## Signing in (AI app → relay)

1. The app registers itself (`POST /oauth/register`, dynamic client registration). Redirect URIs are exact-matched; `https://claude.ai/api/mcp/auth_callback` and `https://claude.com/api/mcp/auth_callback` work like any other registered URI. A client with no compliant redirect is refused by the library.
2. `GET /authorize?…` shows a small page (no scripts, fonts or images, inline CSS, light and dark, 320 px, English or French from `Accept-Language`): the app's name (escaped), where the sign-in goes, "read and edit this list", and one field, the pairing code. The OAuth library's consent helpers carry the request (a one-use handle plus a cookie bound to the browser).
3. `POST /authorize?…` with a valid code completes the authorization with `userId` = the space id and `props` `{spaceId}`. A wrong, used or expired code shows the page again with a plain error and issues nothing. Cancel sends `access_denied` back to the app.
4. Attempts are limited per IP (`RATE_PAIR_IP_PER_MIN`, default 10 a minute) and overall (`RATE_PAIR_ALL_PER_MIN`, default 60; a code doesn't say which space it belongs to, so guesses can't be counted per space). Failed attempts also draw on the IP's general budget. Per space: at most three live codes, and the space's write limit applies when a grant is completed.

Access tokens last an hour; a grant lives while the app keeps refreshing it (idle limit 90 days). Switching off revokes all of them.

## The tools

All answers are plain text, compact lines `id | title | Q1 | due | estimate | project` as the app's AI context uses (`stepLine`). Quadrants: Q1 now, Q2 plan, Q3 quick, Q4 later. A tool error is a normal result with `isError: true` and a sentence saying what to do.

| tool | input | answers |
| --- | --- | --- |
| `today` | none | The date and place; the next step with its starter and resume note; today's list in order with the estimated total and its personal range; the day's shape (from when, until when, the kind of day), when the morning ritual set one; fixed times; steps carried from yesterday; decisions to check; what is done today. Events whose check day (`nudge`) has come are `Check: <title> (id, since D)` rows (`nudgesDue`, from that day until answered; on `get_day` from today on, not for a past day), never on the list; an event done that day is under `Happened`, not `Done`. A step that waits for another is not listed on its own: the head of its chain shows `(+n after, chain due D)` and its quadrant follows the chain's earliest due date. |
| `get_day` | `date` | The same for any date. |
| `query_tasks` | `quadrant?` 1–4, `project?` id or name, `place?` id, name or `any`, `status?` `open` (default) `done` `dropped` `all`, `standing?` (only standing steps), `waiting_for?` (only things the person waits for, with how long and what each holds back), `due_from?`, `due_to?`, `text?` (all words, case and accents ignored), `limit?` ≤ 50 | At most 50 lines, most pressing first (done steps newest first), with the count. Steps that wait are left out (the count line says how many) unless `text` is given; they read `(waiting)`. Standing steps (`template`, the series behind a fixed time that comes back) are listed with `status: all`, or alone with `standing: true`; their title reads `(standing, every day at 20:00)` or `(standing, Mon Thu at 19:00)`. An event (`kind: 'event'`, something waited for) reads `[waiting for, check D]` after its title with `-` for its quadrant, and heads its chain like any head; `waiting_for: true` lists only events (open by default), each with `waiting n days` and `holds back: …`. |
| `get_task` | `id` (an id or a title: an open or done step first, then a standing one; a dropped step only by its id) | The step with its fields and its work sessions; a standing step has a `standing` line (its days, time and lead), a copy placed on a day a `copy of` line naming its series. On a step in a chain, a `chain` line lists its members head first (`>` marks this step) and the earliest due date. |
| `get_project` | `id` (an id or a name) | The goal (`goal:` the outcome, `measure:` and where its bar stands, `starts:`, `moves the goal:` the open steps that advance it; see `goals.md`), the SMART fields, counts, at most 50 open steps. |
| `get_decision` | `id` (an id or a title) | Problem, options with their four columns, the choice, its steps. |
| `read_memory` | `name?` a note id, name or alias, or words that contain one; `query?` free words | What the person told Réussite. Nothing: the profile in full, then the index of the other notes (`id \| kind \| name \| aliases`, newest first, at most 60). A name: the matching notes (by id, name, alias, then a whole-word name in the text, then a unique prefix of whole words) and a query: the notes named in it or with all its words in one line; each note as the app's AI reads it (`noteBlock`, `src/domain/memory.ts`: the head, then the lines numbered from 1) and the open steps that name it (`queryText`, at most 10). At most 8 notes. No match: one sentence and the index. |
| `get_method` | `language?` `en` or `fr` | `METHOD.<lang>.md` and `CHANGESET.md` in short form (bundled as text modules). Needs no list. |
| `apply_changes` | `changes?` (the change-set's list), `note?`, `v?`, `confirm?` | See below. |
| `undo` | `id` | See below. |

Server instructions (sent at initialisation): what Réussite is; call `get_method` before planning or a decision; call `read_memory` when the person names someone, a place or a matter; a new fact goes through `apply_changes` as `memory.add`, in their words, and a memory change always waits for their yes; never change the list without the person's yes except one low-risk change; one `apply_changes` for a quick edit, at most 25 changes in a change-set (more work goes in several); titles work for ids; no weights.

**Addresses and people are not read.** Schema 4 adds the `addresses` and `people` collections to the space (they are in the hot part, so the connector loads them like everything else), but `View` builds neither and no tool or change names them: nothing an AI asks can return an address, a person, a link or a note of theirs (`relay/test/connector.people.test.ts` seeds both and checks every read tool). The one write that touches them is ticking a step that feeds a person (`personId`): `finish` sets the person's `lastSeen` to the day, as ticking it by hand does, and says nothing about them in the receipt. `apply_changes` refuses an `address.create` (the op a trip plan's reply uses in the app): validation rejects the whole change-set, nothing is written, and the error says the person adds addresses in the app.

**Memory is private by construction.** `read_memory` filters out every note with `private: true` before it matches anything, so no id, name, alias or word in a line of a private note finds it, and nothing in an answer says one exists (a miss says only that nothing matches). `apply_changes` leaves them out the same way (step 2 above). The note format is the app's (`noteBlock`): one function writes it for the app's prompts and for this tool.

### `apply_changes`

The input is the contract in `docs/CHANGESET.md` (version 1, same operations). Steps:

1. A change-set holds at most **25 changes** (`MAX_CHANGES` in `relay/src/connector/changes.ts`; it was 80). More: the answer says so, that nothing was written and to split it into several change-sets of at most 25, one call each. The cap is there for the free plan's 10 ms (see "CPU on the free plan"); the app's own AI path (`src/ai/`, `ChangeSetSchema` allows 80) is not limited by the relay, and `docs/CHANGESET.md`, `docs/ai/CHANGESET.md`, the two `today` skills, `get_method`, the `apply_changes` description and the server instructions all tell an AI 25. Then every change is checked with `ChangeSchema`. Any error → nothing is written and **all** errors come back (`Change 2 (task.update): set.due: YYYY-MM-DD`).
2. Titles become ids wherever an id is expected (`task.update/done/drop` ids, `task.reorder`, `day.update`, `set.after`, `set.project`, `set.where`, project and place ids). An id or a ref made in the same change-set is left alone; otherwise the title is matched exactly, then by a unique prefix of whole words, ignoring case, accents and punctuation. Several matches → the candidates come back as lines and nothing is written. No match → "No step with the id or title …", nothing written. A step's title is looked for among the open steps, then the standing steps, then every step. A standing step named by `task.update` or `task.drop` is the series (an update changes its time, days or anything else but never clears its time or days; a drop ends it); named by `task.done`, it is a problem that says to tick the copy placed on the day or drop the series (a tick would close the series). After a write the list's calendar feed is written again, not by the write call but by the maintenance cron (docs/dev/feed.md, "The connector"; below, "Maintenance").
   A memory note (`note` of `memory.*`) is found the same way by id, name or alias, private notes left out; `memory.add` with a `kind` names a new note instead and is not looked up (a name a private note has makes a new open note, exactly as a name no note has). A note that two notes match (the same name or alias) is left alone. A confirmation id keeps each line pinned to its id (`pinLines`), so a yes an hour later edits the line that was shown, and line changes are written on the note as it is then. Notes are read only when a change asks.
3. The set is planned with `planChanges`. Changes that come to nothing (already so) are listed, not written. An event given what only a step has (`est`, `starter`, `due`, `at`, …), or a step given a `nudge`, is refused with its message and nothing is written (`ChangeSchema` for a new or converted one, `Plan.notes` for an update of an event already stored). `task.done` on an event means it happened (`day` may be in the past) and is as low-risk as ticking a step; the connector still puts nothing on a day's list (2026-10-23), so the receipt names the steps it freed (`Freed by it: …`).
4. **One low-risk change** (`isLowRisk` in `src/ai/apply.ts`: a single change that adds a step, ticks one done, or moves one date, meaning only `due`, or `due` and `at`) is applied at once (a memory change never is, and a new standing obligation, one `task.create` with `template`, `weekdays` and `at`, is): one encrypted batch under the device `connector`, a receipt of what changed, the ids created, and an **undo id** (`u…`). The batch and its undo record are one D1 transaction (below). This path has no id, so it cannot be idempotent: if its request is killed after the transaction commits, the AI sees an error although the step was added, and asking again adds it twice. That is why only the smallest changes take it, and the answer is a few milliseconds of CPU.
5. **Anything else** is not written. The answer is the diff (`before → after`) and a **confirmation id** (`c…`), stored encrypted for one hour. Calling `apply_changes` again with only `{"confirm": "c…"}` applies it, once ("Applying a confirmation once"). If the list changed meanwhile so the plan is no longer the same size, the confirmation is dropped and a fresh one is asked for.
6. "R: choir Monday 19:00, Hill House 602" is one call: `{"op": "task.create", "set": {"title": "Choir, Hill House 602", "project": "Choir", "due": "2026-10-26", "at": "19:00", "dur": 90}}`.

**Warnings.** What a write answers must say what an AI would otherwise miss, in the diff (before `Nothing has been written yet`) and in the `Done` answer (before the undo id), the same lines in both (`writeWarnings`, `relay/src/connector/warn.ts`, read from the plan before anything is written; a day is "today", "tomorrow" or `Wed 2026-11-04`; at most six steps are named, then "and n more"):

- `Warning: already on <day>'s list before this: A; B. Keep them, or send \`plan\` with the whole list to replace it.` A `day.update` with `add` and no `plan` over open steps on that day's list (as the app shows it) that the change-set does not name in `add`, `remove` or `first`. An AI laying out a day wrote `add` over an earlier plan and left its steps there.
- `Warning: off <day>'s list but still due <day>: A. Clear \`due\` if they should leave the day.` A step taken off a day's list (`remove`, or left out of a new `plan`) whose due date, as it will be after the change-set, is that day.
- `Warning: due <day> but on no list: A; B. The person may want them on that day's list.` One line a day, for a step made or changed by the change-set that is due tomorrow or earlier, has no time and ends on no day's list. A timed step due that day is not named (it shows among the day's fixed times), nor a far date, nor a step with no date. A step with a time and no day: `Warning: a time but no day, and on no list: A (20:00).`
- `Warning: on <day>'s list but fixed for a later day: A (tomorrow 10:11). It will show on both days. Change its due date if it belongs here, or leave it off this list.` A timed step put on a list earlier than its due date. The app reads the time and the due date as the later day's (calendar, reminders, that day's fixed times: `fixedOn`, `agenda`), and the list as where the person put it, so the step shows on both days. `today` and `get_day` mark such a line on a list `[10:11, fixed for 2026-11-03]`. This is not changed in the app (2026-11-02): a step planned on a day with a time typed in its sheet looks the same, and moving it to its due date would be silent.

The tool texts (server instructions, `apply_changes`, `get_day`), `get_method` and the `today` skills tell an AI to lay a day out with `plan`, read the day back, and read and show the diff and warnings before a yes.

AI-originated fields carry `by: "ai"` / `src: "ai"` as in the app. Weights are never taken from an AI.

### `undo`

Reverts one applied change-set by its undo id. Each document the change-set touched remembers, per field, the value it replaced and the value it wrote (encrypted with the space key, kept 30 days). Undo writes the old values back as **new** changes with fresh clocks, so they reach the app at its next sync. A field the person changed since (its current value isn't the one the change-set wrote) is left alone and named. A document the change-set created is undone with a tombstone (`_del`), never a hard delete, and only if nothing was written to it since (no field with a newer clock than the change-set's) and nothing made since refers to it (a session on a step, a step in a project); otherwise it stays and is named as left alone. A timer that the change-set stopped is not started again by an Undo made much later. An undo id works once: the undo's batch and the deletion of its record are one transaction, conditional on the record still being there, so a kill leaves the id usable and two undos at once write one batch.

The revert itself is `undoWrites` in `src/ai/undo.ts`, the same function the app's Undo uses (`applyUndo` in `src/app/store.ts`); the records are `UndoDoc` (`src/data/schema.ts`), made by `UndoLog`. **Memory:** a change to a memory note records the note's `lines` before and after, so an undo record in `connector_undo` (30 days, encrypted with the space key like the rest) can hold text the person has since forgotten. It is deleted with the record: when used, after 30 days, or when the connector is switched off. A memory line the person forgets in the app is gone from the notes at once, but a record made by the connector before that may still hold its text for up to 30 days; switching the connector off removes them now.

### Applying a confirmation once (a killed request loses nothing)

The free plan stops a request at 10 ms of CPU (error 1102), at any point. A confirmation therefore never disappears before its write, and the write and the mark that it happened are one transaction (D1 runs a `batch()` as one). Migration `0008_connector_lease.sql` adds `claimed_until`, `applied_at`, `undo_id`, `seq` to `connector_pending`.

1. **Claim, don't consume.** `confirmed()` reads the row (`applied_at` set → "Already applied", see 4), plans, then `UPDATE … SET claimed_until = now + 30 s WHERE id = ? AND space = ? AND applied_at IS NULL AND (claimed_until IS NULL OR claimed_until < now)`. No row changed: the answer is either "Already applied" (it was applied between our read and our claim) or "being applied right now by another call, wait a moment and call again with the same id", nothing written, nothing new claimed.
2. **One transaction.** `commit()` seals the undo record first, then `Edits.flush` → `appendBatchWith` (`relay/src/sync.ts`) runs one `DB.batch([…])`: the change batch (`INSERT … SELECT … WHERE` the row is still unapplied: even a lease that ran out under a request that was only slow cannot write a second copy), the connector's clock, the flags the cron reads (`feed_dirty`, `compact_due`), the pruning of old undo rows, the `connector_undo` row, and `UPDATE connector_pending SET applied_at, undo_id, seq`. Statements after the insert are guarded by `EXISTS (SELECT 1 FROM batches WHERE space = ? AND seq = ?)` (a seq belongs to one request), so a skipped insert leaves nothing behind. A request killed before the commit has written none of it; killed after, all of it.
3. **A killed request's lease runs out.** Nothing releases it, so for up to 30 s a retry hears "being applied right now"; after that the same id works. A clean failure (`NeedCold`, over the rate limit, an exception) lets go of the lease at once (`finally`), so the cold-part re-run and a rate-limited retry work immediately.
4. **A retry of an applied id** answers `Already applied: … Undo id: u…` with the original undo id (not an error) and writes nothing. Applied rows are kept until the confirmation's hour is up (the existing pruning of `connector_pending`), then the id is "unknown or expired" as before.

**What is not atomic.** (a) The seq's allocation, `spaceSlot`, the rate-limit statement that bumps `spaces.head`, is its own statement before the transaction: a kill between the two leaves a number unused, a gap that readers ignore (they read `seq > after`), and nothing else; the app's own `POST /batches` has always had it. (b) The one low-risk path (no confirmation id) is atomic in the same way (batch + undo record + clock), but it has no id to retry with, so it cannot be idempotent: a kill after the commit shows the AI an error although the step exists, and a retry writes it again. It is limited to a single add, tick or date move, and the receipt names the id created, so an AI that is unsure can check with `query_tasks`. (c) What the AI is told still depends on the answer reaching it: a request killed after the commit answers nothing, which is why the retry of a confirmation says "Already applied".

### Maintenance (the cron)

A write call has 10 ms and the work after it did not fit, so it is no longer done there. `Edits.flush` and `undo` neither compact nor write the calendar feed; a write only leaves notes in the `connector` row, inside its transaction: `feed_dirty` (the ms of the write), and `compact_due = 1` if the request had to read the cold part (and the opener sets it when a stub points into the cold part). `relay/src/connector/maintain.ts` (`runMaintenance`) is the second cron in `wrangler.jsonc` (`*/5 * * * *`, `MAINTAIN_CRON`; the push tick, `* * * * *`, is left as it was and `scheduled` in `src/index.ts` tells them apart by `controller.cron`, so push sending never shares an invocation with this).

Each run picks **at most one space** and does **one job** for it:

- The space: `connector` rows with `feed_dirty > 0`, or whose hot snapshot is 10 batches behind (`COMPACT_TAIL`) or with `compact_due`, the last two only if the snapshot is in two parts and the space was not picked in the last 15 minutes (`COMPACT_COOLOFF_MS`, so a list that cannot be compacted, or one whose compaction always dies, is not retried every five minutes). Oldest `last_maintained` first. `last_maintained` is set **before** the work, so a run that is killed still sends its space to the back of the line and one heavy space cannot hold the others up.
- The job: compaction if due (`compact` in `space.ts`, with the cold part read first when `compact_due`; `COMPACT_MAX_DOCS` still applies and a list over it is left to the apps, `compact_due` is cleared either way), else the feed (`refreshFeed`; `feed_dirty` is cleared only if no write has come since the run read it). A space that needs both gets the compaction first and the feed at its next turn.
- It reads the space with no cache in either direction: it runs in an isolate of its own, and a copy it left would be one more thing to keep right. A run that is killed loses nothing (the notes stay) and is best effort, like the apps' own snapshots.
- Cache consistency: a compaction made in another invocation folds batches into a new hot snapshot and prunes them. A cached copy stays right: `loadSpace` takes it only if no snapshot newer than the cache's head exists (`upto <= cached.head`, one query with the batches since); otherwise it reads the new snapshot. Tested in `connector.split.test.ts` ("a compaction made by the cron…").

The calendar feed therefore follows a connector write within about five minutes (up to ten if the same space was due for a compaction first), not at once; a device that opens the app still writes it at once.

## Standing series

A standing step (a series: a fixed time that comes back on weekdays) may carry `until`, its last day (inclusive), on `task.create` and `task.update`; `null` clears it, and on a step that is not standing, or on an event, the change-set is refused with the reason. The standing title reads `(standing, Mon at 19:00 until 2026-12-31)`. `today` and `get_day` list a series that comes on the day and whose copy the app has not yet put on the list under Fixed times, marked `[no card on the day yet: …]` (today only those not yet over, a past day none). The connector never writes the copy itself: the app places it when it opens (`placeStandingToday`, a deterministic id per series and day), so a copy can't be made twice, and the server instructions tell the AI not to add a one-off for it.

## Rolling out

The relay is deployed a few minutes **after** the app (docs/dev/sync.md, "Rolling out schema 3", 4 and 5, all the same). A relay that is newer than the app's data writes the new schema at once and puts every device still on the old one into read-only mode. An older relay reads the app's new batches as newer, and every tool says to update the relay and writes nothing. The relay takes its schema number, the change-set validation (`ChangeSchema`) and the planner from the app's source, so any change to those needs the relay deployed too: schema 5 (a step's `label`, a place's `parent`) is one.

## The connector as a device

Its node id is `connector`; its clock is kept per space in D1 (`connector.hlc_wall`, `hlc_counter`) and is moved past every timestamp it reads, so a phone with a fast clock can't make the connector's writes lose against older values. It writes with the same document functions as the app (`create`, `patch`, `remove` in `src/data/doc.ts`), collects what to send with `collectOutgoing` (every field whose clock carries its node and is above the clock it started from), and appends the batch through the same sequence number and per-space rate limit as `POST /batches` (`appendBatchWith`, which adds the clock, the undo record and the confirmation mark to the same transaction). The space is read with `loadSpace` (`relay/src/connector/space.ts`): the snapshot's **hot part** goes straight into maps (it has each document once), later batches are folded in with `applyIncoming`. The cold part is read (`loadCold`, merged under the hot documents) only when something needs it, see "What a call reads". A document from a newer schema than the Worker's `SCHEMA_VERSION` makes every tool answer "update the relay" and write nothing.

Every call updates `connector.last_used` in the same statement that checks the connector is on. When it isn't, `/mcp` answers 403 with a message saying so (normally the token is already revoked and the answer is 401).

## What the relay can read while the connector is on

The whole list: the relay holds the space's key (wrapped; unwrapped in memory for each call) and decrypts it to answer. It also keeps, encrypted with that key, the change-sets waiting for a yes and the undo records. The wrap key (`CONNECTOR_WRAP_KEY`, a Worker secret) never leaves the Worker. Whoever runs the relay could read the space during this time, and only a new recovery key fully undoes having shared it. Switching off deletes the key, the codes, the pending and undo records, and revokes every token. The privacy note in the app says this in plain words, and Settings → Connector (`src/app/ConnectorSettings.tsx`) says it before the button and again in the confirmation. The app asks `GET …/connector` when Settings opens and every ten minutes, keeps `on` and `lastUsed` in `local` for the diagnostics `[connector]` section, and shows the relay's `connector` device row with its last use instead of the row's own `last_seen`.

## What a call reads

A snapshot is in two parts, hot and cold (docs/dev/sync.md, "Hot and cold"). Hot holds what the common questions are about; cold holds finished history. A snapshot written before the split is one whole part and is read whole.

| call | reads |
| --- | --- |
| `read_memory` | hot only (every live note is in the hot part; so are the open steps it lists) |
| `today`, `get_day` (a date in the hot window, 30 days back and all the future), `query_tasks` for open steps, `get_project`, `get_decision`, `get_task` by id for an open or recent step, `apply_changes` and `undo` on open or recent things | hot only |
| `query_tasks` with `status` done, dropped or all; `get_day` for an older date; `get_task` by an id or title that isn't in hot; `apply_changes` naming a step that isn't in hot or a day or step that exists only in cold | hot, then cold |

How it is done: a tool that finds it needs cold throws `NeedCold` before it has written anything, the wrapper in `tools.ts` reads cold and runs it again (a write starts from copies of the maps, so a run that stopped half way leaves nothing behind). Two things keep hot-only answers equal to whole-list answers (a test compares them): the hot header's **index** of cold ids says whether a document that a batch touched, or that a day or decision points to, also lives in cold, and then cold is read first; and its **digest** gives the personal estimate (steps done in the last 400 days, so older ones weigh under 1%) and "steps done" per project (`ColdDigest`; `View.cold`). Titles are looked up among hot steps first, and in cold only if none matches there.

The connector may cut the hot part again (`compact`), but not in a call any more: the maintenance cron does it ("Maintenance"), once 10 batches (`COMPACT_TAIL`) have piled up on it, if the cold part wasn't involved and the hot part is under 600 documents (`COMPACT_MAX_DOCS`; above that gzip alone takes more than a run has left), or when a call had to read cold (it left `compact_due`) and the whole list is in hand. It never rewrites the cold part; the apps do, about weekly. `storeSnapshot` (`relay/src/sync.ts`) is the one place that writes a snapshot, for the HTTP route and for this.

## CPU on the free plan

The free plan gives a request 10 ms of CPU. One call used to decrypt, gunzip and parse the whole snapshot (3.5 MB of JSON for a list of 1,500 steps and 3,000 sessions) and fold up to 50 batches, 25 to 45 ms. Four changes, in the order they were measured (`npm run relay:bench`, median ms of CPU on a laptop, Node's V8; database round trips not counted; `BENCH_SIZE=today` is the owner's list: 281 steps, 110 sessions; the default is the heavy one: 1,500 and 3,000):

| | today's list, read | today's list, `today` | heavy, read | heavy, `today` |
| --- | --- | --- | --- | --- |
| whole snapshot, 30 batches (before) | 12.2 | 11.6 | 31.2 | 36.3 |
| snapshot after 8 batches | 6.1 | 9.3 | 28.4 | 41.4 |
| clocks on the wire as one base clock a document | 5.2 | 6.8 | 21.4 | 27.3 |
| hot part only (the tool's own time also fell by memoising the view: it built an Intl formatter for every line it printed) | 2.7 | 2.3 | 6.1 | 9.2 |
| warm isolate, the cache holds the merged list | 0.3 | 1.1 | 0.3 | 2.6 |

**Memory.** Notes are always in the hot part, so a space with 150 notes of 8 lines (`BENCH_MEMORY`, the default of `npm run relay:bench`) reads about 1.2 ms slower on a cold isolate for every call, `read_memory` or not, and the notes are built into maps only by a call that reads them (`View.memory` is a getter). Measured on a laptop, median ms, cold isolate with no cache, read plus tool (today's list: 281 steps, 110 sessions): `today` 3.1, `read_memory` 2.8, `read_memory` by name with its steps 3.4, `read_memory` by a query that reads every line 4.2; warm isolate 0.4, 0.9 and 1.6. On the heavy list: `today` 10.1 (8.6 without memory), `read_memory` 6.3, by name 9.1, by query 10.8. The tool's own work is 0.3 ms with no arguments, 0.7 by name and 2.6 by query; the rest is the read.

What is left: on the heavy list the hot part is 583 steps and 485 sessions, 480 KB of JSON in 100 KB. Reading it is gunzip 1.3 ms, UTF-8 and `JSON.parse` 1.6 ms, rebuilding each document's `_hlc` 1.9 ms, the tail of 8 batches 0.8 ms; AES-GCM is 0.1 ms. So parsing and rebuilding dominate, not crypto. The tool's own work is 0.2 to 2 ms, the MCP layer 1.2 ms on top. The first call of a fresh process is slower (cold code: 8 to 15 ms at today's size, 20 to 35 at the heavy one). Rewriting the hot part (`compact`) costs 7 ms for today's list (with 150 notes) and 18 ms for the heavy one, mostly gzip, which is why the connector leaves it to the apps above 600 documents, and why it is no longer done inside a write.

**Writes (2 November 2026).** What killed requests: a change-set of 30 changes took 7.6 ms and 80 took 10.2 ms to read, resolve, plan and write on today's list, `compact` added 8 ms whenever it triggered, then the feed (`feedText`, 17 ms on today's list) and the undo seal followed. Four changes: a change-set is at most 25 changes; `compact` and the feed left the write for the cron; the undo seal moved before the append (it is the same work, now in the one transaction); and `formatterFor` in `src/domain/dates.ts` keeps the device-zone formatter for one second (it made a new `Intl.DateTimeFormat` for every reading of a step without a place zone: four per step in `agenda`, so the feed's text fell from 17 ms to 1.7 ms on today's list, and the app's schedules gain too). Measured with `npm run relay:bench` (the new "A change-set of 1, 10, 25 changes" block: a third `task.create` into a project named by its title, a third `task.update` named by title, a third `memory.add` to a note named by its name; cold isolate, median / p95 ms of CPU on a laptop, database round trips not counted). Two calls make a confirmed change-set: the diff (read, validate, titles to ids, plan, describe, pin, seal the confirmation) and the yes (read, decrypt, plan, write, seal the batch and the undo record):

| | today's list: the diff | today's list: the yes | heavy: the diff | heavy: the yes |
| --- | --- | --- | --- | --- |
| one low-risk change (`task.done`), read + plan + write + undo seal | | 4.0 / 6.6 | | 10.0 / 12.7 |
| 1 change | 4.0 | 3.9 | 9.8 | 9.7 |
| 10 changes | 4.4 | 5.8 | 11.1 | 11.0 |
| 25 changes (the cap) | 4.9 | 5.4 | 12.8 | 11.5 |
| warm isolate, one low-risk change | | 1.0 | | 1.4 |
| first call of a fresh process, 1 / 10 / 25 changes (cold code, Node) | 17.8 / 22.4 / 24.1 | 14.8 / 19.3 / 21.0 | 29 / 34 / 40 | 26 / 31 / 33 |

So on today's list a 25-change set costs about as much as a read plus a millisecond or two, in each of its two calls; the cap of 80 was 10 ms by itself. The heavy list (1,500 steps) is over the budget on the read alone (7.6 ms), as before; the first call of a fresh process is slower for every call, reads included (`today` 14 ms), and is not what this change addresses.

The maintenance runs, in a cron invocation of their own (same list, median ms, steady / first call of a fresh process): compaction, read then rewrite the hot part, **10.9** / 21 on today's list (over 10 ms: best effort, and a run killed here loses nothing; gzip is 7 of it); the feed, read then `feedText`, **4.6** / 13 on today's list. The heavy list's runs are 27 and 10 / 48 and 23.

**The cache.** A module-level LRU in the Worker isolate (`relay/src/connector/cache.ts`) keeps the decrypted, merged maps of up to 3 spaces (24 MB by a rough count), keyed by space and the wrapped key, with the highest seq they contain. A call that finds its space there reads only the batches after that seq (plus a small query that checks no newer snapshot folded batches away and the space still exists). It is an optimisation: a new isolate starts empty, and the benchmark reports the cold-isolate number (no cache) as the guarantee and the warm one apart. It holds plaintext in the isolate's memory only while the connector is on, which doesn't change the trust model: the relay already holds the key then, and everyone who can run the Worker can read the list as it is. An entry is dropped when the connector is switched off or the space deleted (in the isolate that handles that), when it is switched on again (the wrapped key differs), after 5 minutes idle, and to stay within its budget. Other isolates can't be reached from the one that handles the switch-off, but every call first runs the statement that checks the connector is on, so a stale entry there can never answer; it is gone with its isolate or after 5 idle minutes. A call that writes works on copies of the maps it changes, and a refused write leaves the cache alone.

## Running it

`relay/.dev.vars` (gitignored; see `.dev.vars.example`) holds `CONNECTOR_WRAP_KEY` (`openssl rand -base64 32`) and `RELAY_URL`. `npm run relay:dev`, `npm run relay:test`, `npm run relay:bench`. To deploy: set `RELAY_URL` and the real names and ids in `relay/wrangler.jsonc`, create the KV namespace `OAUTH_KV`, run the D1 migrations (`0008` before the relay that uses it is deployed), `wrangler secret put CONNECTOR_WRAP_KEY`. The Worker has two crons (every minute: push; every five: the maintenance) and observability on. Check the bundle with `wrangler deploy --dry-run --outdir out` (about 360 KiB gzipped; the free plan allows 3 MiB).
